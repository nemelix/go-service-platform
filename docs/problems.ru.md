# С чем столкнулся

Проблемы, на которые я наткнулся по ходу проекта: что увидел, почему так было, что сделал и какой вывод. Самые интересные есть и в [README](../README.ru.md).

## Деплой и Docker

### На сервере работала старая версия, хотя деплой прошел

**Симптом:** CI зеленый, деплой отработал без ошибок, а на сервере отвечала прошлая версия.

**Причина:** образы помечались только тегом `latest`. На сервере и в registry под одним и тем же `latest` лежали разные образы, и по тегу нельзя было понять, какой из них запущен.

**Решение:** каждый образ получает тег с sha коммита, а скрипт деплоя принимает только sha. Теперь по тегу точно видно, какой код работает, а откат - это деплой прошлого sha.

**Вывод:** изменяемые теги вроде `latest` не годятся для того, что разворачивается на сервер.

### Контейнер падал с `exec /server: no such file or directory`, хотя файл на месте

**Симптом:** образ собирался, а контейнер сразу завершался с этой ошибкой. Файл `/server` в образе при этом был.

**Причина:** без `CGO_ENABLED=0` Go собрал бинарник динамическим: ему нужны libc и динамический загрузчик. В distroless/static их нет, и ядро не может запустить файл. Сообщение «no such file» относится к загрузчику, а не к самому бинарнику.

**Как нашел:** `ldd server` на этапе сборки показал зависимости от libc.

**Решение:** `CGO_ENABLED=0` при сборке. Получается статический бинарник, которому ничего не нужно.

**Вывод:** «файла нет», когда файл точно есть, - это почти всегда загрузчик, архитектура или CRLF в shebang.

### Старые образы не удалялись после деплоя

**Симптом:** после нескольких деплоев на сервере копились образы приложения, место уходило.

**Причина:** `docker image prune` удаляет только образы без тега (dangling), а у моих у каждого есть тег sha.

**Решение:** `docker image prune -af` с фильтром по label `org.opencontainers.image.source`, который ставит Dockerfile. Удаляются все неиспользуемые образы именно этого проекта, чужие не трогаются.

**Вывод:** label в Dockerfile полезен не только для GitHub, по нему удобно отбирать свои образы.

## Сеть и SSH

### Порт контейнера был доступен из интернета, хотя в ufw он закрыт

**Симптом:** порт, опубликованный через `-p`, открывался снаружи, хотя ufw его не разрешал.

**Причина:** Docker публикует порты своими правилами iptables (DNAT). Такой трафик идет по цепочке FORWARD, а правила ufw стоят в INPUT, и до них пакет не доходит.

**Решение:** наружу публикуется только Nginx (80/443). Приложение доступно лишь внутри сети Docker, Nginx обращается к нему по имени сервиса.

**Вывод:** с Docker фаервол на хосте не защищает опубликованные порты. Защита - не публиковать лишнее, привязывать к `127.0.0.1` или писать правила в цепочку `DOCKER-USER`.

### Вход по паролю в SSH был включен, хотя в `sshd_config` стоял `no`

**Симптом:** в `/etc/ssh/sshd_config` было `PasswordAuthentication no`, но сервер принимал пароль.

**Причина:** `sshd_config` подключает файлы из `sshd_config.d/` в самом начале. В `50-cloud-init.conf` стояло `PasswordAuthentication yes`, а в sshd побеждает **первое** найденное значение, не последнее.

**Как нашел:** `sshd -T` выводит итоговые настройки, которые sshd реально применяет.

**Решение:** исправил значение в `50-cloud-init.conf` и проверил через `sshd -T`.

**Вывод:** итоговую конфигурацию проверяю командой, а не чтением одного файла.

### Не хотел давать GitHub полный доступ к серверу

**Задача:** CI должен деплоить на сервер, но ключ в GitHub - это ключ к серверу для любого, кто его получит.

**Решение:**
- отдельный пользователь `deploy` без пароля и sudo;
- его ключ в `authorized_keys` ограничен через `restrict` и forced command: при любом подключении запускается только скрипт деплоя;
- скрипт принадлежит root и принимает только 40-символьный sha коммита.

**Вывод:** даже если ключ утечет, с ним можно только развернуть один из уже собранных образов.

## CI

### Линтер нашел настоящий баг

**Симптом:** golangci-lint (errcheck) указал на непроверенную ошибку `http.ListenAndServe` в `main.go`.

**Как проверил:** запустил два контейнера в одном сетевом пространстве (`--network container:`), чтобы второй не смог занять порт 8080. Второй контейнер завершился со статусом `Exited (0)` и пустым логом, как будто отработал нормально.

**Причина:** `ListenAndServe` вернул ошибку «address already in use», ее никто не проверил, `main` закончился, процесс вышел с кодом 0.

**Решение:** `log.Fatalln("error:", http.ListenAndServe(...))`: ошибка пишется в лог, код выхода - 1.

**Вывод:** errcheck - не придирка. Проглоченная ошибка превращает падение в «успешное завершение».

### golangci-lint локально проходил, а в CI падал

**Симптом:** локально 0 замечаний, а в CI:
```
could not import internal/goarch (... export data version 5 is greater than maximum supported version 4) (typecheck)
```

**Причина:** локально я запускал `latest`, а в CI была закреплена v2.13, собранная до выхода Go 1.27. Она не умела читать стандартную библиотеку новой версии Go.

**Решение:** закрепил v2.15 - ту, что была в `latest`.

**Вывод:** версию линтера обновляю вместе с версией Go. Dependabot ее не обновит: в workflow это просто строка в `with:`.

### PR можно было смержить, хотя линтер упал

**Симптом:** джоба `lint` красная, а кнопка Merge зеленая.

**Причина:** обязательной проверкой в ruleset был только `build`. Когда `lint` падал, `build` (он зависит от `lint` через `needs`) получал статус skipped, а GitHub считает пропущенную обязательную проверку успешной.

**Решение:** добавил в обязательные проверки каждую джобу: test, golangci-lint, hadolint, shellcheck, gitleaks, build.

**Вывод:** при переименовании или добавлении джобы надо обновлять и список обязательных проверок.

### Trivy остановил публикацию образа

**Симптом:** джоба `build` упала на шаге Trivy, push в ghcr и деплой не выполнились.

**Причина:** HIGH-уязвимость в `crypto/x509` из стандартной библиотеки Go 1.27.2. Сам я x509 не вызываю (TLS снимает Nginx), но пакет вшит в бинарник через `net/http`, а сканер не знает, какой код реально вызывается.

**Решение:** исправление вышло в патч-версии. Поднял Go до 1.27.3 в Dockerfile и `go.mod`.

**Вывод:** уязвимости в Go-приложении чаще всего не в моем коде, а в стандартной библиотеке, и лечатся обновлением Go. Неисправленные уязвимости (`ignore-unfixed`) сборку не блокируют, иначе CI был бы красным постоянно.

### Теги GitHub Actions оказались ненадежными

**Что случилось:** в марте 2026 у `aquasecurity/trivy-action` перезаписали почти все теги на вредоносный код, который воровал секреты CI. Все, кто писал `uses: aquasecurity/trivy-action@v0.x`, получили чужой код, не меняя ни строчки у себя.

**Решение:** сторонние actions закреплены по полному sha коммита с версией в комментарии: `uses: owner/repo@<sha> # v1.2.3`. Тег можно перевесить на другой коммит, а sha - нет. Sha ищу через `git ls-remote`: у аннотированного тега нужна строка с `^{}`, это коммит, а не объект тега. Обновления присылает Dependabot.

**Вывод:** `uses:` - это запуск чужого кода с доступом к секретам, и доверять ему нужно так же осторожно, как зависимостям в коде.
